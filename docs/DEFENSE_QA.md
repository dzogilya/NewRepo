# 20+ запитань та відповідей для захисту проєкту перед викладачем

### 1. Чому саме PostgreSQL використовується як координатор черги задач, а не RabbitMQ чи Kafka?
**Відповідь:** Це ключова вимога еталонної схеми викладача (БД як єдине джерело істини). Зберігання черги безпосередньо в реляційній БД гарантує сувору консистентність: якщо запис створено, він гарантовано буде оброблений. Використання окремого брокера створило б проблему розподіленої транзакції (Dual Write Problem), коли в базі запис зберігся, а в брокер не відправився через мережевий збій.

### 2. Як гарантується, що два app-сервери ніколи не захоплять одну й ту саму задачу?
**Відповідь:** За допомогою конструкції PostgreSQL:
```sql
SELECT id FROM tasks WHERE status='Queued' AND app_server_id IS NULL AND is_canceled=false
ORDER BY created_at, id FOR UPDATE SKIP LOCKED LIMIT 1
```
`FOR UPDATE` блокує знайдений рядок на рівні БД, а `SKIP LOCKED` наказує всім іншим транзакціям миттєво пропускати заблокований рядок і переходити до наступного без очікування. Атомарний `UPDATE ... RETURNING *` закріплює сервер за задачею в межах тієї ж транзакції.

### 3. Що станеться, якщо Redis тимчасово перестане відповідати чи перезапуститься?
**Відповідь:** Система не втратить жодної задачі. Redis використовується виключно як допоміжний шар (Pub/Sub поштовхи та SSE стріми). Усі App-сервери мають низькочастотний фоновий опитувач БД (`PeriodicTimer`), тому навіть за повної відсутності поштовхів із Redis воркери продовжують вибирати задачі з PostgreSQL. Клієнти автоматично перемикаються з SSE на polling endpoint `GET /api/tasks/{id}`.

### 4. Що буде, якщо впаде PostgreSQL? Як усунути це в продуктивному середовищі?
**Відповідь:** У поточній навчальній конфігурації один інстанс Postgres є єдиною точкою відмови (SPOF). У реальному продакшені це вирішується за допомогою:
- Кластера PostgreSQL із реплікацією (наприклад, Patroni + HAProxy або AWS Aurora / Managed RDS Multi-AZ).
- Read/Write розділення та автоматичного failover на репліку при збої Primary.

### 5. Що буде, якщо впаде Nginx? Як забезпечити високу доступність Web-шару?
**Відповідь:** В одинарній інфраструктурі падіння Nginx зупинить прийом нових HTTP-запитів. Для production розгортається кілька екземплярів Nginx за протоколом VRRP (Keepalived) з плаваючим віртуальним IP (VIP), або використовується хмарний балансувальник L4/L7 (AWS ALB, Cloudflare, Google Cloud Load Balancer).

### 6. Чому обрано Server-Sent Events (SSE), а не WebSockets чи Long Polling?
**Відповідь:** 
1. SSE є односпрямованим протоколом (Server -> Client), що на 100% відповідає задачі трансляції прогресу.
2. Працює по стандартному протоколу HTTP/HTTPS без необхідності протокольного апгрейду до WS.
3. Має вбудовану в браузерний `EventSource` підтримку автоматичного перепідключення.
4. Значно легший для проксі-серверів (Nginx) і не потребує додаткових фреймворків (SignalR).

### 7. Чому Data Protection ключі ASP.NET Core мають зберігатися у спільному сховищі?
**Відповідь:** За замовчуванням ASP.NET Core зберігає ключі шифрування cookie та антифорджері токенів локально на диску ноди. Оскільки за Nginx працюють дві ноди (`api1` та `api2`), cookie, видана `api1`, на наступному запиті потрапить на `api2` і не зможе бути розшифрована (користувач отримає розлогін). Збереження ключів у Redis через `PersistKeysToStackExchangeRedis` забезпечує єдиний простір ключів для всіх API-інстансів.

### 8. Як реалізовано захист від IDOR (Insecure Direct Object Reference)?
**Відповідь:** Кожен ендпоінт перегляду або модифікації задачі (`/api/tasks/{id}`, `/api/tasks/{id}/cancel`) витягує `UserId` із валідованого JWT-токена користувача і перевіряє:
```csharp
if (!User.IsInRole("admin") && task.UserId != currentUserId)
    return Forbid();
```
Користувач Б не може скасувати або переглянути задачу користувача А, навіть якщо знає її GUID.

### 9. Чому для обчислення використовується `Parallel.For`, а не Task на кожен піксель?
**Відповідь:** Створення окремого `Task` для кожного з 2-10 мільйонів пікселів створило б колосальне навантаження на Garbage Collector і пул потоків (thread pool starvation). `Parallel.For` по рядках (з обробкою блоками пам'яті через сирі покажчики/span) розбиває роботу на кількість частин, пропорційну кількості ядер процесора, забезпечуючи максимальну утилізацію CPU без зайвих алокацій пам'яті.

### 10. Як працює механізм Watchdog і як уникається дублювання його роботи?
**Відповідь:** Watchdog запускається на app-серверах як `BackgroundService`. Щоб кілька серверів не виконували перевірку одночасно, використовується вибір лідера через PostgreSQL advisory lock: `SELECT pg_try_advisory_lock(777888)`. Лідер знаходить задачі зі статусом `Running`, чий `heartbeat_at` застарів більш ніж на 15 секунд, і повертає їх у `Queued` (якщо ліміт `attempts < 3`), або переводить у `Failed` з кодом `SERVER_TIMEOUT`.

### 11. Як захищена система від нескінченних повторів «задач-вбивць» (poison pills)?
**Відповідь:** Кожна задача має лічильник `attempts`. Якщо задача спричиняє падіння сервера і перезапускається більше 3 разів, Watchdog остаточно маркує її як `Failed`, запобігаючи нескінченному циклу падінь серверів.

### 12. Як працює безпечний Scale-Down в Autoscaler, щоб не втратити задачу, яка обчислюється?
**Відповідь:** Autoscaler перед зупинкою контейнера аналізує зайнятість серверів через БД:
```csharp
var busyServers = await db.Tasks.Where(t => t.Status == "Running").Select(t => t.AppServerId).ToListAsync();
```
Контейнер зупиняється ТІЛЬКИ якщо на ньому немає жодної активної задачі (`activeTasks == 0`). Базові сервери (`app-node-1`, `app-node-2`) ніколи не зупиняються (дотримується `MIN_APP_SERVERS = 2`).

### 13. Чому трудомісткість розраховується як $W \times H \times MaxIter$?
**Відповідь:** Кожен піксель у найгіршому випадку (всередині множини фрактала) виконує до $MaxIterations$ комплексних множень і додавань. Тому добуток розмірів на кількість ітерацій прямо пропорційний кількості арифметичних операцій з рухомою комою і часу роботи процесора.

### 14. Як розраховується орієнтовний час очікування (ETA) в черзі?
**Відповідь:** За формулою:
$$\text{ETA} = \frac{\sum \text{Cost попередніх задач у черзі}}{\text{Кількість активних серверів} \times \text{Слоти} \times \text{Пропускна здатність на слот (Cost/сек)}}$$
Пропускна здатність калібрується бенчмарком (~2.5 млн оп/сек на ядро процесора).

### 15. Як реалізовано захист від XSS та CSRF?
**Відповідь:** 
- XSS: Клієнтський код не використовує небезпечний `innerHTML` із неперевіреним користувацьким вводом; імена та параметри екрануються або вставляються через `textContent`.
- CSRF: Запити використовують Bearer-токени в заголовку `Authorization`, а для cookies встановлено атрибути `SameSite=Lax`, `HttpOnly` та `Secure`.

### 16. Чому використано SkiaSharp замість System.Drawing.Common?
**Відповідь:** Починаючи з .NET 6, `System.Drawing.Common` офіційно підтримується виключно на Windows (залежить від GDI+). У Linux-контейнерах спроба виклику `System.Drawing` кидає `PlatformNotSupportedException`. SkiaSharp кросплатформенний, підтримує апаратне прискорення та бездоганно працює в Linux.

### 17. Чому для паролів обрано Argon2id, а не MD5 чи SHA-256?
**Відповідь:** Швидкі геш-функції (MD5, SHA-256) вразливі до перебору на GPU (мільярди гешів на секунду). Argon2id — переможець Password Hashing Competition (PHC), має налаштування споживання пам'яті (64 МБ) та кількості ітерацій, що робить апаратний перебір на ASIC/GPU економічно невиправданим.

### 18. Що таке Rate Limiting і де він налаштований?
**Відповідь:** Реалізовано на двох рівнях:
1. Nginx: директива `limit_req` для обмеження кількості HTTP-запитів з однієї IP-адреси.
2. ASP.NET Core: `Microsoft.AspNetCore.RateLimiting` з фіксованим вікном (100 запитів на хвилину на користувача).

### 19. Які слабкі місця та компроміси є в поточній реалізації?
**Відповідь (чесна інженерна оцінка):**
1. Доступ до `docker.sock` для Autoscaler створює потенційний ризик безпеки (у продакшені слід використовувати Kubernetes Horizontal Pod Autoscaler - HPA замість прямого сокета).
2. Спільне файлове сховище (`shared_storage`) в продакшені повинно бути об'єктним сховищем (S3 / MinIO) із роздачею через CDN, а не спільним томом файлової системи.

### 20. Як довести викладачу, що Nginx дійсно балансує трафік?
**Відповідь:** Кожна відповідь API містить заголовок `X-Served-By` з унікальним `INSTANCE_ID` ноди (`api-node-1` або `api-node-2`). При повторних запитах у DevTools / curl видно чергування цих значень.
