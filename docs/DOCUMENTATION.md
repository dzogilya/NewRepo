## 1. Призначення

HeatLab рахує стаціонарний розподіл температури у квадратній пластині. Користувач задає:

- розмір сітки **N** (пластина N×N точок);
- максимальну кількість ітерацій **K**;
- температури чотирьох країв: верхнього, нижнього, лівого, правого.

Сервер розв'язує рівняння Лапласа методом Якобі й повертає теплову карту. Обчислення розподілені між кількома серверами застосувань; балансувальник відправляє кожну задачу на вільний сервер, а якщо всі зайняті — запускає новий сервер, ставить задачу в чергу або відмовляє.

**Технології:** C# / .NET 8, ASP.NET Core, Entity Framework Core + SQLite, HTML + CSS + JavaScript без фреймворків.

## 2. Запуск і зупинка

Потрібен лише [.NET 8 SDK](https://dotnet.microsoft.com/download/dotnet/8.0). Окремо встановлювати базу даних не треба: SQLite — це файл.

| Команда | Що робить |
| :--- | :--- |
| `run.bat` | Зупиняє старі процеси HeatLab, збирає проєкт, запускає систему |
| `run.bat fresh` | Те саме, але спочатку видаляє базу даних `storage/heatlab.sqlite` |

Що відбувається після запуску:

1. `run.bat` вбиває процеси `HeatLab.exe`, що лишилися від попереднього запуску (щоб звільнити порти).
2. `dotnet build` збирає проєкт у конфігурації Release.
3. Запускається `HeatLab.exe` без аргументів — це **шлюз з балансувальником**. Його консоль і є вікном `run.bat`.
4. Шлюз створює/відкриває базу, відкриває браузер на <https://localhost:7443> і запускає у фоні (без вікон) два сервери застосувань: `HeatLab.exe server server-1 5101 <PID шлюзу>` і `server-2` на порту 5102.

Логи серверів друкуються у вікні шлюзу з префіксом `[server-N]`. У цьому ж вікні видно кожне рішення балансувальника, наприклад `Задача #24 → server-2 (зайняті: server-1)`.

**Зупинка:** закрити вікно шлюзу або натиснути Ctrl+C. Шлюз вбиває дочірні процеси, а кожен сервер додатково стежить за PID шлюзу і вимикається, коли той зник.

**Обліковий запис адміністратора** створюється автоматично: `admin` / `admin123`.

| Адреса | Призначення |
| :--- | :--- |
| <https://localhost:7443> | Сайт (головна сторінка) |
| <https://localhost:7443/login.html> | Вхід і реєстрація |
| <https://localhost:7443/admin.html> | Адмін-панель |
| <http://localhost:7080> | Перенаправляє на HTTPS (код 301) |

Сертифікат самопідписаний, тому браузер попередить про небезпеку: «Додатково» → «Перейти на localhost».

## 3. Архітектура

Уся система — **одна програма** `HeatLab.exe`, яка працює в одній із двох ролей залежно від аргументів командного рядка.

```text
                        HTTPS :7443
  Браузер ─────────────────────────────▶  ШЛЮЗ = веб-сервер + LOAD BALANCER
  (HTML/JS, опитування                    • сторінки сайту, HTTPS
   кожну секунду)                         • вхід, історія, скасування, адмінка
                                          • Balancer: кому віддати задачу?
                                                  │
                     POST /run/{id} — лише вільному серверу
                 ┌────────────────┬───────────────┼────────────────┐
                 ▼                ▼               ▼                ▼
             server-1         server-2        server-3         server-4
              :5101            :5102           :5103            :5104
             (базові, працюють завжди)     (додаткові, запускаються
                 │                │          автоматично, коли всі зайняті)
                 │   прогрес і результат      │                │
                 ▼                ▼               ▼                ▼
          ┌────────────────────────────────────────────────────────────┐
          │      SQLite storage/heatlab.sqlite  —  Users · Tasks        │
          └────────────────────────────────────────────────────────────┘
                 ▲
                 └── шлюз теж читає й пише сюди (користувачі, задачі, черга)
```

### Ролі

| Роль | Як запускається | Що робить |
| :--- | :--- | :--- |
| **Шлюз / балансувальник** (gateway) | `HeatLab.exe` | Єдина точка входу по HTTPS. Віддає сторінки, обробляє вхід і всі запити `/api/*`. Вирішує, на який сервер відправити задачу. Запускає, перезапускає й вимикає сервери |
| **Сервер застосувань** (application server) | `HeatLab.exe server <id> <port> <gatewayPid>` | Тільки рахує: отримує номер задачі, читає параметри з БД, розв'язує, пише прогрес і результат у БД. Рахує одну задачу за раз |

Це той варіант, який дозволяє завдання: «в ролі load balancer може виступати і сам веб-сервер, а задачі виконуються на кількох серверах застосувань».

### Як компоненти спілкуються

- **Браузер → шлюз:** тільки HTTPS. Браузер не знає про існування серверів застосувань.
- **Шлюз → сервер:** HTTP-запит `POST http://localhost:510N/run/{id}` — «порахуй задачу № id». Сервер відповідає `202 Accepted` і починає рахувати у фоні, або `409 Conflict`, якщо зайнятий.
- **Сервер → БД:** сервер сам пише прогрес (кожні 0.5 с), результат або помилку в таблицю `Tasks`.
- **Шлюз → БД:** шлюз читає з таблиці `Tasks` стан задач і показує його користувачу.
- **Сервери ↔ сервери:** напряму не спілкуються.

## 4. Балансування навантаження

Це найважливіша частина завдання. Балансувальник — клас `Balancer` у шлюзі. Round Robin (роздача по колу) **не використовується**: задача йде не «наступному по черзі», а серверу, який зараз **вільний**.

### Правило вибору сервера

Сервер зайнятий, якщо в таблиці `Tasks` є задача зі статусом `Running` і його `ServerId`. Кожен сервер рахує лише одну задачу одночасно.

Коли з'являється нова задача (або звільняється сервер), балансувальник іде по серверах за номером:

```text
server-1 вільний?            → відправити йому
інакше server-2 вільний?     → відправити йому           («перший зайнятий — на другий»)
інакше server-3, server-4…   → відправити першому вільному
усі зайняті:
   серверів < 4              → запустити новий сервер (п. 7), задача чекає в черзі
   черга < 4 задач           → поставити в чергу, повідомити позицію і час (п. 6)
   черга заповнена           → ВІДМОВА У ВИКОНАННІ (HTTP 503)
```

Сам вибір — одна функція `Balancer.PickServer`: перший сервер зі списку готових, якого немає в списку зайнятих.

### Коли балансувальник роздає задачі

1. **Одразу при створенні задачі.** `TasksController` записує задачу в БД (`Queued`) і викликає `Balancer.DispatchAsync()`. Тому користувач у відповіді бачить, куди пішла задача: «Задачу #24 відправлено на server-2» або «Усі сервери зайняті — задачу #25 поставлено в чергу: позиція 1, очікування ~30 с».
2. **Щосекунди у фоні.** Якщо сервер звільнився, наступна задача з черги відправляється йому.

### Як відправляється задача

1. У БД задача атомарно переводиться в `Running` з `ServerId` вибраного сервера (`UPDATE … WHERE Id = @id AND Status = 'Queued'`).
2. Шлюз надсилає серверу `POST /run/{id}`.
3. Якщо сервер не відповів або відповів помилкою — задача повертається в чергу, сервер позначається «неготовим», балансувальник пробує інший сервер.

Усі операції балансувальника виконуються під одним замком (`SemaphoreSlim`), тому одна задача ніколи не потрапить на два сервери і на один сервер не потраплять дві задачі.

### Автоматичне масштабування

- **Вгору:** якщо після роздачі в черзі лишилися задачі, усі сервери зайняті, жоден не стартує і серверів менше 4 — запускається наступний (`server-3`, потім `server-4`). Новий сервер стає готовим приблизно за секунду, і задача з черги одразу йде на нього.
- **Вниз:** якщо додатковий сервер (3 або 4) не рахує і черга порожня 30 с поспіль — шлюз завершує його процес. Базові сервери 1 і 2 працюють завжди.

## 5. Сайт: сторінки та сценарії користувача

Сайт складається з трьох статичних HTML-сторінок. Дані сторінки отримують від API через `fetch` і оновлюють опитуванням (polling).

### 5.1. Вхід / реєстрація — `login.html`

- Одна форма: ім'я користувача + пароль.
- Посилання під кнопкою перемикає режим «Вхід» ↔ «Реєстрація».
- Підказка `admin / admin123` показується лише в режимі входу.
- Після успіху браузер отримує cookie `heatlab_auth` і переходить на `/`.

Правила реєстрації: ім'я щонайменше 3 символи і унікальне; пароль — будь-який непорожній.

### 5.2. Головна сторінка — `index.html`

**Шапка:** ім'я користувача, посилання «Адмін-панель» (тільки для ролі admin), кнопка «Вийти».

**Картка «Нова задача»:** поля N, K і чотири температури країв з межами `min`/`max`, кнопка «Запустити розрахунок». Перед відправкою JavaScript перевіряє межі й трудомісткість N·N·K (перевірка на клієнті). Під кнопкою показується:

- синім — куди пішла задача або що вона в черзі з позицією й часом очікування;
- червоним — помилка: заважка задача, забагато активних задач, відмова у виконанні.

**Таблиця «Мої задачі»** (оновлюється щосекунди, останні 50):

| Стан | Колонка «Де / черга» | Кнопки |
| :--- | :--- | :--- |
| В черзі | позиція і приблизний час очікування | Скасувати |
| Рахується | сервер, ітерація `i / K`; смужка прогресу | Скасувати |
| Готово | час завершення | Показати, Видалити |
| Помилка | текст помилки | Видалити |
| Скасовано | час завершення | Видалити |

**Картка результату** (після «Показати»): теплова карта на `<canvas>`, під нею шкала кольорів від синього (мінімум) до червоного (максимум). Праворуч — кількість ітерацій, чи досягнута збіжність, мінімум/максимум, час обчислення.

### 5.3. Адмін-панель — `admin.html`

Доступна лише ролі `admin`. Оновлюється кожні 2 с.

- **Лічильники:** кількість серверів (максимум 4), **навантаження** у відсотках (зайнято X з Y серверів), задач у черзі (максимум 4), що рахуються, готових, з помилкою, скасованих.
- **Сервери:** ім'я, порт, PID процесу, тип (базовий / додатковий), стан (вільний / рахує / запускається), поточна задача, скільки задач виконав, час запуску.
- **Усі задачі (останні 50)** всіх користувачів: власник, трудомісткість N·N·K, стан, прогрес, сервер, час створення, кнопка «Скасувати» для активних.

### 5.4. Скрипти і стилі

| Файл | Вміст |
| :--- | :--- |
| `js/api.js` | `api(path, method, body)` — обгортка над `fetch`, повертає `{ok, status, data}`; `esc()` — екранування HTML (захист від XSS); `formatWait`, `formatTime`, `logout`; `STATUS_UA` — українські назви станів |
| `js/heatmap.js` | `heatColor(t)` — колір для t ∈ [0, 1] (HSL, 240° синій → 0° червоний); `drawHeatmap`; `drawLegend` |
| `js/app.js` | Головна сторінка: `init`, `validateInputs` (перевірка на клієнті), `sendTask`, `refresh`, `rowHtml`, `onTaskButton`, `showResult` |
| `js/admin.js` | Адмін-панель: `refresh` і скасування задач |
| `css/style.css` | Єдиний файл стилів |

## 6. HTTP API

### 6.1. API шлюзу (для браузера, тільки HTTPS)

Тіла запитів і відповідей — JSON. Помилки: `{ "message": "текст українською" }`.

**Авторизація — `AuthController`:**

| Метод | Адреса | Доступ | Відповідь |
| :--- | :--- | :--- | :--- |
| POST | `/api/auth/register` | усі | 200 + cookie; 400 некоректні дані; 409 ім'я зайняте |
| POST | `/api/auth/login` | усі | 200 + cookie; 401 невірні дані |
| POST | `/api/auth/logout` | усі | 200, cookie видаляється |
| GET | `/api/auth/me` | увійшли | 200 `{username, role}`; 401 |

**Задачі — `TasksController` (потрібен вхід):**

| Метод | Адреса | Відповідь |
| :--- | :--- | :--- |
| GET | `/api/tasks` | Масив власних задач (до 50) зі станом, прогресом, сервером, позицією в черзі й часом очікування |
| POST | `/api/tasks` | Тіло `{size, iterations, top, bottom, left, right}`. 200 `{id, message}` — відправлено на сервер або поставлено в чергу; 422 параметри поза межами; 429 вже 5 активних задач; **503 відмова у виконанні** (усі сервери зайняті, черга заповнена) |
| GET | `/api/tasks/{id}/result` | `{mapSize, map[], iterations, converged, min, max, seconds}`; 404 |
| POST | `/api/tasks/{id}/cancel` | 200 `{message}`; 404 |
| DELETE | `/api/tasks/{id}` | 200; 409 задача ще активна; 404 |

**Адміністрування — `AdminController` (роль `admin`):**

| Метод | Адреса | Відповідь |
| :--- | :--- | :--- |
| GET | `/api/admin` | Лічильники, `busyServers`, `maxServers`, `maxQueue`, масив `servers`, масив `tasks` |
| POST | `/api/admin/tasks/{id}/cancel` | 200 `{message}` |

Не увійшли — 401, не адмін — 403.

### 6.2. API сервера застосувань (тільки для шлюзу, `http://localhost:510N`)

| Метод | Адреса | Відповідь |
| :--- | :--- | :--- |
| POST | `/run/{id}` | 202 — почав рахувати задачу; 409 — уже рахує іншу |
| GET | `/healthz` | `ok` — сервер запустився і готовий приймати задачі |

## 7. База даних

Файл `storage/heatlab.sqlite`, режим журналу WAL (читання не блокують запис), таймаут очікування блокування 30 с. Таблиці створюються автоматично під час першого запуску. Усі дати зберігаються в UTC.

### Таблиця `Users`

| Поле | Тип | Опис |
| :--- | :--- | :--- |
| `Id` | int, PK | Ідентифікатор |
| `Username` | text, унікальний | Ім'я |
| `PasswordHash` | text | Хеш пароля (PBKDF2) |
| `Role` | text | `user` або `admin` |

### Таблиця `Tasks`

| Поле | Тип | Хто пише | Опис |
| :--- | :--- | :--- | :--- |
| `Id` | int, PK | шлюз | Номер задачі; порядок у черзі — за зростанням `Id` |
| `UserId` | int | шлюз | Власник |
| `Params` | text (JSON) | шлюз | Параметри N, K, температури |
| `Cost` | long | шлюз | Трудомісткість N·N·K |
| `Status` | text | шлюз і сервер | `Queued`, `Running`, `Success`, `Failed`, `Cancelled` |
| `ServerId` | text | балансувальник | Сервер, якому віддано задачу |
| `Progress`, `Iteration` | int | сервер | Прогрес у % і поточна ітерація |
| `IsCanceled` | bool | шлюз | Прапорець «користувач попросив скасувати» |
| `Result` | text (JSON) | сервер | Зменшена карта ≤ 100×100 і статистика |
| `Error` | text | сервер | Текст помилки |
| `CreatedAt`, `StartedAt`, `FinishedAt` | datetime | обидва | Час створення, початку, завершення |

Окремої таблиці серверів немає: шлюз сам запускає процеси серверів і тримає їхній список у пам'яті, а зайнятість визначає за задачами `Running`.

## 8. Життєвий цикл задачі

```text
       POST /api/tasks ── черга заповнена ──▶ 503 «Відмова у виконанні» (задача не створюється)
              │
              ▼
         ┌─────────┐   скасування    ┌───────────┐
         │ Queued  │────────────────▶│ Cancelled │
         └─────────┘                 └───────────┘
           │     ▲                         ▲
 балансув. │     │ сервер упав              │ IsCanceled = true
 відправив │     │                          │
           ▼     │                          │
         ┌─────────┐────────────────────────┘
         │ Running │──── понад 120 с або виняток ──▶ ┌────────┐
         └─────────┘                                 │ Failed │
              │ збіжність або K ітерацій             └────────┘
              ▼
         ┌─────────┐
         │ Success │
         └─────────┘
```

Покроково:

1. Користувач натискає «Запустити». JavaScript перевіряє межі. Шлюз ще раз перевіряє параметри й ліміти і записує задачу `Queued`.
2. Балансувальник шукає вільний сервер. Знайшов — ставить `Running` + `ServerId` і надсилає серверу `POST /run/{id}`. Не знайшов — задача лишається в черзі (і, якщо можна, запускається новий сервер).
3. Сервер рахує й кожні 0.5 с пише `Progress`, `Iteration`, перевіряє `IsCanceled`.
4. Сторінка щосекунди запитує `/api/tasks` — шлюз читає ці поля з бази.
5. Наприкінці сервер записує `Success` і `Result` (або `Failed` / `Cancelled`). Сервер вільний — балансувальник віддає йому наступну задачу з черги.

| Метод | Що робить |
| :--- | :--- |
| `CancelAsync(db, id)` | Задачу з черги одразу робить `Cancelled`; для `Running` ставить `IsCanceled = true` — сервер сам зупиниться |
| `RequeueAsync(db, serverId)` | Задачі `Running` вказаного сервера (або всіх, якщо `null`) повертає в `Queued` |

### `Gateway/GatewayApp.cs`

1. Перевіряє, що порти 7080, 7443, 5101–5104 вільні.
2. Ініціалізує базу, повертає в чергу задачі `Running`, що лишилися з минулого запуску.
3. Kestrel: HTTP 7080 і HTTPS 7443; перенаправлення HTTP → HTTPS (301); заголовок HSTS.
4. Cookie-авторизація (`HttpOnly`, `Secure`, `SameSite=Lax`), ключі шифрування у `storage/keys`.
5. Сторінки з `frontend/`, контролери API, `Balancer` як фонова служба.
6. Відкриває браузер.

`LoadOrCreateCertificate` створює самопідписаний сертифікат RSA-2048 на `localhost` у `storage/gateway-cert.pfx`.

### `Gateway/Balancer.cs`

- **`AppServer`** — опис одного сервера застосувань: номер, порт, процес, PID, «готовий», з якого часу простоює.
- **`PickServer`** — вибір першого вільного сервера.
- **`DispatchAsync`** — роздати задачі з черги вільним серверам і, якщо треба, запустити новий сервер. Викликається при створенні задачі.
- **`ExecuteAsync` / `TickAsync`** — під час старту запускає `server-1` і `server-2`, потім щосекунди: перезапускає впалі базові сервери й повертає їхні задачі в чергу; перевіряє `/healthz` серверів, що стартують; роздає задачі; масштабує вгору і вниз.
- **`Launch`** — запускає `HeatLab.exe server server-N 510N <PID шлюзу>` як прихований процес, перенаправляє його вивід у консоль шлюзу.
- **`StopAsync`** — при зупинці шлюзу вбиває всі сервери.

### `Gateway/AuthController.cs`, `TasksController.cs`, `AdminController.cs`

- **Auth** — реєстрація, вхід, вихід, `me`; паролі хешуються `PasswordHasher` (PBKDF2 із сіллю).
- **Tasks** — `POST` перевіряє параметри, ліміт активних задач, заповненість черги (інакше — відмова 503); обрізає історію до 50; записує задачу; викликає балансувальник і повідомляє, куди пішла задача. Також список, результат, скасування, видалення.
- **Admin** — сервери (з балансувальника) зі станом і поточною задачею, навантаження, лічильники, останні 50 задач.

### `Server/ServerApp.cs`

Сервер застосувань. Слухає `http://localhost:<port>`, має дві адреси:

- `GET /healthz` — «я запустився»;
- `POST /run/{id}` — якщо вільний, починає рахувати задачу у фоні й відповідає 202; якщо зайнятий — 409.

`ComputeAsync` читає параметри задачі з БД, запускає `HeatSolver` з лімітом 120 с, кожні 0.5 с пише прогрес і перевіряє `IsCanceled`, наприкінці пише `Success` + `Result`, `Failed` або `Cancelled`. Усі записи мають умову «задача моя і `Running`», тож сервер не зіпсує задачу, яку вже повернули в чергу. Сервер вимикається, коли зникає процес шлюзу.

## 10. Алгоритми

### 10.1. Метод Якобі

Стаціонарна теплопровідність описується рівнянням Лапласа ∂²T/∂x² + ∂²T/∂y² = 0. На сітці кожна внутрішня точка дорівнює середньому чотирьох сусідів:

```text
T_new[i, j] = ( T[i-1, j] + T[i+1, j] + T[i, j-1] + T[i, j+1] ) / 4
```

Метод Якобі повторює це, читаючи старий масив і записуючи в новий, потім масиви міняються місцями. Краї не змінюються — це граничні умови. Зупинка: найбільша зміна за ітерацію < 10⁻³ (**збіжність**) або виконано K ітерацій.

Складність O(N²·K) — звідси міра трудомісткості N·N·K. Перевірка: при одному гарячому краї 100 °C і трьох холодних у центрі точно 25 °C — це перевіряє тест.

### 10.2. Оцінка часу очікування

Метод `TaskQueue.QueueInfoAsync` враховує розмір кожної задачі:

1. **Швидкість** v — з останніх 20 успішних задач: сума їхнього часу / сума їхньої трудомісткості N·N·K (секунд на одиницю). Якщо готових задач ще немає — 1.5·10⁻⁹ с.
2. **Коли звільниться кожен сервер.** Для задачі, що рахується: `Cost · v · (100 − Progress) / 100`. Сервери, яких ще немає, але які балансувальник може запустити (усього до 4), вважаються вільними одразу.
3. **Розклад черги.** Задачі з черги беруться по порядку; кожна дістається серверу, що звільниться найраніше. Цей момент і є її очікуванням, після чого сервер зайнятий ще на `Cost · v`.

```text
приклад: 4 сервери рахують задачі по ~27 с, у черзі 4 такі самі задачі
→ кожна чекає, поки звільниться «свій» сервер: оцінка 22–24 с (реально 26–33 с)
```

## 16. Як показати викладачу

Задача N = 600, K = 50 000 рахується ~30 с — цього достатньо, щоб усе показати.

1. Запустити `run.bat`. У вікні шлюзу видно запуск `server-1`, `server-2` і «готовий приймати задачі». Відкрити адмін-панель в окремій вкладці (`admin` / `admin123`).
2. Користувач **A** запускає задачу: «Задачу відправлено на **server-1**».
3. Друга задача: «відправлено на **server-2**» — перший зайнятий, тому на другий. У вікні шлюзу: `Задача #… → server-2 (зайняті: server-1)`.
4. Третя: обидва зайняті → у вікні шлюзу «МАСШТАБУВАННЯ ВГОРУ», запускається `server-3`, задача йде на нього. Четверта — на `server-4`.
5. П'ята: «Усі сервери зайняті — задачу поставлено в чергу: позиція 1, очікування ~25 с».
6. Шоста: «У вас уже 5 активних задач (максимум 5)» — **ліміт задач користувача**.
7. Користувач **B** (вікно інкогніто) запускає ще три задачі — вони стають у спільну чергу (позиції 2–4). Четверта: «**Відмова у виконанні**: усі сервери зайняті, а черга заповнена».
8. В адмінці: 4 сервери «рахує», навантаження 100 %, черга 4. Скасувати одну задачу — звільнений сервер одразу бере задачу з черги.
9. Відмовостійкість: завершити процес `server-1` у диспетчері задач (PID видно в адмінці) — його задача повертається в чергу і йде на інший сервер, `server-1` перезапускається.
10. Коли все порахується, через 30 с `server-3` і `server-4` вимкнуться («МАСШТАБУВАННЯ ВНИЗ»).
11. Перевищення трудомісткості: N = 1000, K = 50 000 — помилка «Задача завелика».

## 17. Типові проблеми

| Симптом | Причина і рішення |
| :--- | :--- |
| «Порти … зайняті іншою програмою» | Працює стара копія або інша програма. `run.bat` сам вбиває старі HeatLab; якщо порт тримає інша програма — закрийте її |
| Браузер пише «З'єднання не захищене» | Самопідписаний сертифікат. «Додатково» → «Перейти на localhost» |
| Збірка: файл `HeatLab.exe` заблокований | Сайт ще працює. Просто запустіть `run.bat` — він зупиняє старі процеси |
| «Перевищено ліміт часу» | Задача рахувалась довше 120 с. Зменште N або K |
| Результат без збіжності | K замале для такого N. Збільште K або зменште N |
| Забули пароль адміністратора / зіпсована база | `run.bat fresh` — база створиться заново з `admin / admin123` |
